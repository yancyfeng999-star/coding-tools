## 1. 背景

仓库已经包含 MIT `LICENSE`，但公开协作所需的入口不完整：贡献者不知道如何提交代码或目录变更，安全问题没有私密披露入口，用户支持与行为准则缺失，GitHub Issue/PR 也没有结构化模板。README 仍承担过多职责，第三方依赖与目录内容的许可边界没有单独说明。

本次设计只补齐开源项目的公开协作层，不修改 Swift 业务代码，不改变安装器、目录验签或发布脚本行为，也不构建或打开 macOS App。

## 2. 目标与非目标

### 目标

1. 让新用户能从 README 找到项目定位、运行方式、许可证、支持和安全入口。
2. 让贡献者能按统一流程提交代码、目录、文档和 Bug 修复。
3. 让安全研究者能绕过公开 Issue，使用 GitHub 私密安全报告入口。
4. 明确本项目代码、第三方依赖、工具名称/商标、外部教程和目录数据的权利边界。
5. 让 GitHub Issue 与 Pull Request 默认收集足够的复现和审查信息。

### 非目标

- 不更换现有 MIT License。
- 不把 Sparkle、Homebrew、mise、工具供应商内容或其商标重新授权为本项目内容。
- 不新增遥测、账号系统、远程服务或社区平台。
- 不把 `.app`、`build/`、DerivedData、私钥、用户配置或本地日志纳入仓库。
- 不在本轮修改产品功能或执行 App 构建验收。

## 5. GitHub 协作流

1. README 链接到贡献、安全、支持和行为准则；各文档互相链接但不重复完整法律文本。
2. Bug 模板要求版本、macOS、架构、复现步骤、期望/实际结果、日志脱敏状态。
3. 功能模板要求使用场景、替代方案、权限/隐私影响和是否涉及第三方内容。
4. PR 模板要求说明变更范围、验证方式、目录签名影响、许可证来源和是否生成了本地 App/构建物。
5. `config.yml` 关闭空白 Issue，保留安全报告和支持入口；安全问题不得使用公开 Issue。
6. 现有 CI 继续作为代码变更的构建/测试入口；文档变更不要求在维护者机器上构建或打开 App。

## 6. 安全与隐私公开口径

`SECURITY.md` 使用 GitHub Private Vulnerability Reporting 入口：
`https://github.com/yancyfeng999-star/coding-tools/security/advisories/new`。

公开文档必须提醒用户：不要提交 Token、私钥、Cookie、用户配置、绝对路径、安装日志原文或可复现漏洞细节。安全报告应包含受影响版本、影响范围、最小复现、临时缓解和联系方式；维护者确认后再决定修复版本、公告和披露时间，不承诺未经验证的 SLA。

`docs/OPEN_SOURCE_GUIDE.md` 说明当前产品边界：设置、缓存、日志和安装状态默认保存在本机；目录签名私钥不入库；第三方内容只保存允许公开的元数据和链接；本项目不因收集诊断信息而自动获得用户文件或凭证。

## 7. 验证与交付门槛

本轮只执行文档范围的检查：

- 所有新增 Markdown/YAML 文件存在且无占位符、空链接和相互矛盾的许可证说法。
- README 中的新增链接均指向仓库内存在的文件或明确的 GitHub 页面。
- YAML Issue 模板可解析，字段 ID 唯一，安全入口不要求公开漏洞信息。
- `git diff --check` 通过；不出现 `.app`、`build/`、DerivedData、密钥或用户数据。
- Git 状态只包含本轮开源文档变更；不运行 `xcodebuild`、`tuist build` 或 App 启动。
